# Notion Service憲章

## 核となる原則

### I. サービス優先アーキテクチャ
すべての機能は、集中的なFirebase Cloud Functionとして実装する必要があります。関数は自己完結型で、独立してデプロイ可能であり、単一のビジネス目的に奉仕する必要があります。Notion API統合、データ変換、レスポンスフォーマットの間の明確な分離が必要です。

### II. TypeScript標準
すべてのコードは、厳密な型チェックが有効になったTypeScriptで記述する必要があります。型定義は包括的でなければならず、すべてのデータ構造、APIレスポンス、関数パラメータをカバーする必要があります。十分に文書化された外部API統合を除き、`any`型は許可されません。

### III. テストカバレッジ
すべてのサービス関数とヘルパーユーティリティにはユニットテストが必須です。すべてのモジュールでテストカバレッジは80%を超える必要があります。Notion APIの相互作用とデータ変換パイプラインには統合テストが必要です。

### IV. Firebase統合
すべての関数は、適切なエラーハンドリング、タイムアウト設定、メモリ最適化を含むFirebase Functionsのベストプラクティスに従う必要があります。関数は、該当する場合、認証とデータアクセスにFirebase Admin SDKを使用する必要があります。

### V. API設計
すべてのエンドポイントは、適切なHTTPステータスコードを持つ一貫したJSONレスポンスを返す必要があります。エラーレスポンスは、内部実装の詳細を公開せずに意味のあるメッセージを含む必要があります。すべてのパブリックエンドポイントでAPIドキュメントを維持する必要があります。

### VI. 日本語コミュニケーション標準
すべてのAIアシスタントの応答は、入力言語に関係なく日本語でなければなりません。すべてのドキュメントファイル（.md）には対応する日本語版が必要です。コードコメントと技術ドキュメントは、より良いチームコミュニケーションとアクセシビリティのために日本語を優先する必要があります。

## セキュリティ要件

すべてのNotion APIキーと機密設定はFirebase環境変数に保存する必要があります。すべての外部データソースには入力検証が必要です。エラーログには機密情報やAPIキーを含めてはいけません。

## 開発ワークフロー

すべての変更には、デプロイ前にユニットテストが通過する必要があります。コードフォーマットと品質チェックにはESLintとPrettierを使用する必要があります。TypeScriptコンパイルは警告なしで成功する必要があります。関数はデプロイ前にFirebaseエミュレータを使用してローカルでテストする必要があります。

## ガバナンス

この憲章は他のすべての開発プラクティスに優先します。すべてのコードレビューはこれらの原則への準拠を検証する必要があります。修正には、既存コードの合理的根拠と移行計画の文書化が必要です。
